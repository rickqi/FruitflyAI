## 0. 判定摘要（TL;DR）

**一句话**：Fly64 的「振荡陷阱 / 终态卡死」不是一个控制参数问题，而是**自适应信号（学习、增益、参数、教练建议）到"决定行为的变量"之间没有信用分配通路**（M1），叠加**仲裁层只有固定优先级表、没有竞争/升级语义，且四个可用于升级或逃离的原生机制各自被别的机制锁死**（M2）；两者长期不可见的原因是**观测/检测层存在成体系的单位与口径缺陷**（M3，其中 `stuck_score≡1.0` 是构造伪影，报告引以为据的"卡死"证据部分不成立）；**自进化闭环**（M4）在运行性、诊断面、输出形态、适应度四节同时断开，因此既发现不了也修不了——且它当前唯一的可执行输出形态恰好就是被本团队排除的硬编码控制补丁。

| 序 | 主因 | 层级 | 性质 | 若不解决 |
|---|---|---|---|---|
| **M3** | 观测/检测层口径缺陷（单位契约、门限语义、伪影外溢） | 观测 | **解锁条件** | M1/M2 的真伪与效果都无法判定（报告两条主根因已被证明不可复现即为此代价） |
| **M1** | 信用分配断口：决定行为的变量与所有自适应面不重叠 | 决策/输出 | **决定性主因** | M3/M4 的任何修复都只能在饱和解码器的输入腿上做**无效微调**（实证：60.3% 试验 delta 恰为 0） |
| **M2** | 仲裁层无竞争/无升级 + 逃离机制可达性被别的机制锁死 | 仲裁 | **直接主因** | 即使 M1 打通，遇到新型陷阱仍无换策略能力 |
| **M4** | 进化闭环运行性 + 诊断面 + 输出形态 + 适应度 | 进化闭环 | **必要条件（非行为成因）** | 修复只能靠人工发现（实证：停摆 7 天、台账靠人手写到 EVO-073） |

**必须与主因分开的两类"非事实"**：
1. **检测层伪影**：`stuck_score=1.0`、`stuck_duration=1100.72s` 在 HEAD 上是**构造产物**（§3 有完整机制与独立复核），不是卡死的证据；报告依赖它们的结论（"反射疲劳"）随之失去立足点。
2. **版本边界**：唯一可复现的行为证据 `.tmp/fly64_trajectory.json` 与 HEAD 静态结构**不相容**（§1.4），因此报告（及其 7 层链）描述的是一个**更早修订的运行点**。

## 3. 检测层伪影 vs 真实行为卡死：因与果

### 3.1 分离判定表

|---|---|---|---|
| 位置/位移序列（`x,y,z,t`） | ✅ 是 | 真实观测量 | `.tmp/fly64_trajectory.json` 6000 点，可复算 |

| X/Z 效率、waste_ratio、coverage、loop_score | ✅ 是（但**分类不同**） | 真实症状量，**不是卡死定义** | §1.2 |

### 3.2 因果次序（正面回答"何者为因、何者为果"）

```
单位契约缺陷(M3: per-tick 比例 vs 5.0 Hz)
   ⇒ stuck_score ≡ 1.0 (构造)                 ← 果1：指标失真
   ⇒ stuck_duration 单调增长 (泄放被覆盖)      ← 果2：时间量失真
   ⇒ main.py:2687 外溢进 model.stuck_duration
       ⇒ CX 环路突破的 stuck 输入是伪影（model.py:2096）
       ⇒ burst 前置是伪影（main.py:2056）⇒ HEAD 下 burst 会以伪影为条件触发
       ⇒ 逃逸门是伪影（memory.py:2186）⇒ escape_behavior 被抬升
       ⇒ 参考"报告 run"的 burst 从未触发（§1.4）⇒ **伪影已经把该 run 与 HEAD 分离**
   ⇒ "卡死"的**观测**与"卡死"的**事实**脱钩
```

**判定**：
1. **检测伪影是因、报告中的"卡死证据"是果**——但对于**真实行为卡死**（终态 545 帧静止、23.1% 静止帧、X 净后退 3739 u），伪影**既不是因也不是果**，它是**另一条独立故障线上的产物**；两者的唯一交点是**伪影污染了以它为输入的自适应面**（上图中的外溢链）。
2. **因此必须分开处理**：真实卡死程度只能从**轨迹运动学**重算（我已在 §1.2 给出）；而任何以 `stuck_*` 为输入的门（burst/逃逸/CX/反射冷却/EVO 匹配）在使用前必须重建口径。
3. **对主因排序的影响**：伪影使 M3 上升为**解锁条件**而非"又一个 bug"——因为**不修 M3，M1/M2 的修复效果无法被观测**（同一个原因也解释了报告为何会把 M1/M2 误判为"控制层/反射层"问题，以及 t2 §5 的 60.3% 零 delta：fitness 建立在失真的观测量上）。

## 4. (b) 反证与替代解释考察

### 4.1 振荡是主因，还是"转向增益永不被抑制"的表现？

**判定：振荡是症状，不是主因；"转向增益永不被抑制"的方向对但口径要修正。**

- **证据（饱和解码）**：`raw_x = clip(turn_rate*1100, ±70)`（`model.py:2283`）。增益 1100 意味着 `|turn_rate| ≥ 6.36%` 即打满 ±70；实测前 5455 采样点**从未回到 0**、满量程占 88.8%（§1.2）⇒ 观测到的"疯狂切换"是**饱和非线性对近零净输入的放大**。所谓"控制器频率过高"是输出层的重述。
- **证据（两侧才是因）**：
  - 净转向输入在 0 附近反复变号（"竞争胜者频繁翻转"）；
  - 能把净输入推向一侧的**导航信号量级不足**：CX 转向电流经两级小增益后 ≤0.018 V/tick（t1 S11），而转向竞争主导项 ±0.18 V/tick（t1 S28，`model.py:345-392,1477-1520,2132-2166`）⇒ **差 10 倍，导航无法打破平局**；
  - 而这套主导腿**不在 dopamine 增益空间内**（与 jump 池同型，t1 §1.3 的"增益盲"清单）⇒ **任何学习/增益机制都无法把该振荡"抑制/衰减"**。精确表述是："**主导转向腿不在任何自适应空间内，且导航腿量级不足以打破平局**"，而不是"增益没有被抑制"（增益确实在动，只是动不到这条腿）。
- **反证检验**：若振荡是主因，则①"限制单帧变化 ≤±20/死区"（报告 P1.1）应能恢复效率；②振荡强度应与效率损失单调相关。但：
  - ①是控制补丁，属排除路线，且**没有可用的判据检验其效果**——因为判据（`stuck_score`）是伪影，而 fitness 不可分辨（t2 §5）；
  - ②无法建立：效率损失发生在**前 5455 点**（未到终态），而"终态静止"与"振荡"是同一输出的两个相位，不是两个独立量。
  ⇒ **无证据支持"振荡为主因"；有结构证据支持"振荡 = 饱和解码 + 净零竞争"的表象。**
- **待验证假设 H1'**：0.37 s 级变号的**生成者**究竟是谁——候选是 R14/R16 转向回路疲劳/反驱动（`model.py:345-392,1477-1520,2132-2166`，唯一具备"符号反转/疲劳"结构的主导量级腿），也可能是别的竞争项。**需要 `/flow.json` 的 `ctrl_x` 原序列 + 各驱动腿分解**才能定量确认；本机无法离线复现真实连接组（§1.5）。

### 4.2 反射疲劳是主因，还是"仲裁器为固定优先级表、缺少竞争与升级"的表现？

**判定：都错位了。"反射疲劳"不是主因，而且它连一个可靠现象都不是；真正的缺陷是仲裁结构（M2）。**

- **"反射疲劳"不成立的三条独立理由**：
  1. 它依赖 `stuck_score=1.0`，而该值是构造伪影（§1.3）；
  2. `memory.json` 的分类结果在 HEAD 上不可复现（§2.1-#4/#6，`_vote` 顺序 + `escape_behavior` 被伪影抬升）；
  3. 轨迹显示**反射层从未取得操纵权**（`ctrl_y∈{50,70}`；无反思反射的 30、无 burst 的 127、无 CPG 的 ±60/±69 群，t1 §6 + §1.2）⇒ 该 run 的行为由 LIF 解码独占，不是"反射在跑却放弃"。
- **反证检验（本次发现，力度最强）**：若"反射在运行但放弃"，则在与 `stuck_score≡1.0` 同源的 HEAD 条件下，burst（`control.y=127`，占空比 200/500 tick，`main.py:2055-2086`）**必须**出现；实测 **0/6000**（§1.4）。这同时否证了"反射疲劳"，并暴露版本边界 H1。
- **真正成立的是仲裁结构缺陷（M2）**，而且它不是"优先级顺序写错了"，是**四类语义的整体缺失**：
  - **无竞争**：`_vote()` 首命中即返回（`memory.py:1361-1373`），没有任何机制让两个候选策略"对比/竞争"；
  - **无升级**：进入某类后，只能靠"别的类条件先满足"而被动退出，**没有"处理无效则升级"的语义**（报告 P1.4 想加的正是这个，但它写成"再触发一次 oscillating"= 又一次控制补丁 + 无判据可判"无效"）；
  - **无超驰**：`wall_stuck` 与 `stuck_ramp` 相互孤立，`escape_behavior` 同时是两者的前置（`memory.py:1319-1321, 2183-2191`）⇒ 一旦它为假，两个检测一起失明（t2 §2.2 的"自锁"）；
  - **可升级路径全部被别的机制锁死**：CX 环路突破（`central_complex.py:286-306`）、CPG 原语（`main.py:2521-2530`）、oscillating 反射（`memory.py:1289-1317`）、自举突破（`memory.py:2094-2105`）——四个机制各自拥有一个**恒真/恒假前置**。
- **对 t1 的一处修正（证据纪律）**：t1 把 `forced_bold_explore`（S24）判为"结构上不可达"，理由是报告 run 的 `anomaly_duration=11.14 s` 反复重置。该判断建立在不不可复现的 `memory.json` 上，且 `bold_explore_stuck_s` 是被静默钳位的教练可调参数（t2 §4-C3：活值 60 vs 注册区间 [1,10]）⇒ 钳位后阈值 ≤10 s，可达性显著上升。**我据实修定为：可达性依赖"钳位后的阈值 + 单一异常标签的稳定性"，属待验证假设（H4），不作为"结构不可达"断言。**

### 4.3 闭环停摆是主因，还是"fitness 不可分辨 + 输出形态单一"的后果？

**判定：两者不是同一因果线上的因与果，必须分开；停摆属"组织性/运行性因"，fitness 与输出形态属"设计性因"，二者共同构成 M4，但都不是行为故障（振荡/卡死）的成因。**

- **停摆的直接原因与 fitness 无关**（t2 §1.2、§7）：无 python 进程 / 无 `.evo_loop.lock` / 无计划任务 / 唯一数据源 dashboard `127.0.0.1:8765` 不可达（"无法连接到远程服务器"）⇒ `Waiting for dashboard...` ⇒ **连 finding 都不产生**。此外 4.46 天内 iteration 归零重启 **≥9 次**（t2 §1.4）⇒ 它从来不是一个受管进程。
- **"fitness 不可分辨 + 输出形态单一"不是停摆的后果**，是独立存在的设计缺陷，且**在闭环运行期内就已被观测到**：
  - 68 个唯一试验中 **41 个 delta 恰为 0.0（60.3%）**、66/68 的 `|delta| ≤ 0.03`、**commit 率 1.47%**（t2 §5）；
  - 19 条 fix 中 **16 条零可执行代码**（7 行代码 vs 87 行注释）；**8/16 pattern 的 fix_files 指向 `main.py`**；唯一的真实控制写入 `fix_0013` = `control.x = rng.integers(60,80); control.y = 40`，且 `effective=false`（baseline 458.98 → post 464.72）（t2 §3.1–§3.2）；
  - 漏斗：`13728 iter → 44159 findings → 11 fixes → 11 verified → 0 effective`（t2 §6）。
- **反证检验（决定性）**：若"停摆"是"未被自治修复"的主因，则闭环**运行期**（2026-09-12 23:26 → 2026-09-17 10:22）应当有可观测修复成果；实测该窗口内 `effective=0`、漏斗最后一节归零、且该窗口 top pattern 前四位**已包含与本故障最相关的 `ramp_trap`（命中 5631 次）**，却未产出任何有效修复（t2 §2.4、§6）⇒ **停摆不是"未修复"的充分解释，故不是主因**。
- **反向检验**：若只修 fitness 与输出形态而进程仍无守护，则"7 天无人知晓"照旧发生（t2 §1.1）⇒ M4 内部两条**并列、缺一不可**。
- **注意一个逻辑陷阱（必须写明）**：`ramp_trap` 的 5631 次命中发生在**闭环死亡之前**，而把它改瞎的 `048fd16`（`position_unchanged_30s` 零生产者）落地于 **2026-09-18**，**比闭环死亡晚 1 天**（t2 §4-C1）⇒ **"自进化把自己改瞎"这件事发生在闭环已经不在运行的时候**——它既非"运行时错误决策"，也非"人工错误"能单独解释，而是**没有运行时观测覆盖 + 没有复核门**的必然结果（属 M4/M3 交界）。

3. **M2 不解决 ⇒ 即使 M1 打通，系统遇到新型陷阱仍无换招能力**。M1 让学习/进化能改变行为，但"改变哪个行为"仍由固定判定表决定；四个升级机制的可达性锁不清除，"升级"就永远不发生。
4. **M4 不解决 ⇒ M1/M2/M3 只能靠人工发现**（实证：停摆 7 天后，EVO-073 之前的一切都由人工台账推进，t2 §1.5）。
5. **循环依赖与破环点**：M1 ↔ M4 互为前提——M1 给闭环"可起作用的作用点 + 可分辨的适应度"，M4 给 M1"被发现与被验证的能力"。**破环点就是 M3**：先统一观测与门限语义、把闭环的观测值落盘，M4 才能有可信 fitness，M1 才能被搜索到，行为改变后 M2 的升级语义才能被检验。
   ⇒ **建议实施顺序：M3（观测/语义）→ M1（作用点）→ M2（仲裁结构），M4 与 M3 并行（存活自检 + 元指标告警 + 审计落盘）。**

### 6.2 论证：为什么 B 类（自治能力缺失）比 A 类（硬性缺陷）更根本

1. **覆盖性（逻辑论据）**：A 类决定"信息是否正确"，B 类决定"系统能否改变自己"。
   - A 类全部修好，系统仍然只会**正确地执行它原有的、不可学习、不可升级的策略**——`stuck_score` 从不失真地等于 0 也不会让它逃出振荡陷阱（因为它本来就没有"学到一个新策略"的通路）；
   - B 类修好（有了作用点、有了升级语义、有了可分辨适应度、有了情景责任链），A 类即使残留也会**被观测到并被搜索修掉**（例如 A3 死写入会被"写值→观察消费点变化"的运行时 A/B 直接暴露，t2 §4-C4 已把 A/B 定为确定性判据）。
2. **实证论据（已发生的事实）**：闭环运行 4.46 天、13728 iter、44159 findings、11 fixes、11 verified、**0 effective**（t2 §6）；19 条 fix 中 16 条根本没有可执行代码（t2 §3.2）。⇒ **"打补丁"这一路线在真实数据上已经被证明不产生能力积累。**
3. **作用域论据（本次复核）**：唯一可复现的 run 中，控制权在 LIF 解码层（`ctrl_y∈{50,70}`、无 127/30、t1 §6 + §1.2），memory/reflex/CPG 层**从未参与**。⇒ 修那些层（报告 P0.1/P0.2/P0.3）不会改变该运行点的行为；而 M1/M2 才会。
4. **脆弱性论据（现场自述，最有力）**：`main.py:2040-2054` 的注释记录了一次真实的补丁失效——补丁 A 的前置条件读 `anomaly_state=="oscillating"`，而"**同一个位移门在果蝇高速编织时把它钉成 idle**"，于是该补丁"**在报告的那种形态下永远打不开**"。加上 `_deadlock_burst_ready` 的改绑发生在 **2026-09-23 08:36**（`6d0aa42`，`git log -S`），而唯一可复现的 run 与 HEAD 在"是否 burst"上**可观测地不相容**（§1.4）⇒ 结论：**硬补丁不是"次优解"，而是"脆弱解"——它的可达性依赖其它机制的输出恰好合法，而本系统里恰恰有多处机制互相钉死对方的输入**（A3 死写入、A4 无消费者门限、A7 空守卫、A8 零生产者键、A9 静默钳位，同一族）。
5. **失败模式的对称性**：报告 P0.1/P0.2 与 t2 查到的 `fix_0013` 是**同一路线的两个实例**（写死 `control.x/y`、反射里塞 jump），前者未落地、后者落地且 `effective=false`（t2 §3.2）。⇒ 这条路线**已经被尝试过，且已被数据否证**。

**结论**：A 类必须修（它们是 M1/M2/M3 的可修复入口，且修它们**不违反**"排除硬编码控制补丁"——单位契约、死写入、零生产者键、门限口径统一都是"让已有信号真正到达"，不新增控制分支），但**方案的核心必须是 B 类**：给系统一个能到达行为变量的作用点、一套能竞争与升级的仲裁语义、一份能分辨差异的适应度、一条情景化的责任链。

## 8. 对最终方案 `docs/analysis/fly64-autonomy-evolution-plan.md` 的判定性输入

以下为**判定结论**，不是建议清单（建议由方案任务产出）：

1. **不能再把主因写成"控制层/反射层"**。报告的 7 层链的 4/5/6/7 层建立在旧修订 + `stuck_*` 伪影上（§1.3、§1.4、§3）。方案若沿用该链条，会把资源投到"给反射加 jump"（=排除路线 + 归因错误）。
2. **M3 必须作为第一步**，且它**不是控制补丁**：统一门限语义（唯一执行门 `model.py:2478` + 单位对齐）、切断伪影外溢（`main.py:2687` → `model.py:2096` 等）、把闭环的**观测值**落盘（现在只记 finding id，t2 §1.3）。没有这一步，"是否变好"无法判定。
3. **M1 的可行修复形态必须全部是"让已有信号到达"，不得新增控制分支**：把 MBON→jump 腿纳入增益链（`model.py:1787` × `gain("jump")`，取代固定 0.35）、给跳池一个与 `forward_homeo_gain`（`model.py:1452-1475`）对等的自稳态、把 `jump_rate > 0.04` 改成**归一化量**（例如相对前向池占用率），把两处死写入的写端改到 `_goal_comp`（`main.py:1848-1851`）。这五项恰好是 t1 §8.8 列出的同一族，本判定独立复核为**唯一与 M1 因果结构对齐的修复面**。
4. **M2 的修复形态必须是"竞争 + 升级 + 超驰"语义**，而不是"降低某个阈值"或"再加一个门"。特别地：报告 P1.3/P1.4（降低 oscillating 阈值 / stuck_ramp 后升级）方向对但**写成常量仍是控制补丁**；本判定的口径是**让检测窗自适应于实测交替周期**（`memory.py:1289-1317` 的 30 帧窗 vs 实测 ≈0.37 s 翻转）、**把"处理无效则升级"定义为状态机的显式转移**、并**清除四条原生路径的恒真/恒假前置**（`central_complex.py:286-306`、`main.py:2521-2530`、`memory.py:2094-2105`）。
5. **fitness 必须以可分辨量为准**，且必须换成长时间窗：现有 120 s 瞬时窗（`main.py:1419-1425`）与 `stuck_*` 伪影叠加是 60.3% 零 delta 的直接来源；可用量如 `waste_ratio` / 净位移 / 环行分数 / 覆盖率增量的**长窗**，并要求 A/B 双向复现（t2 §8.3）。
6. **方案必须包含"闭环存活 + 元指标告警"**：无守护、失败静默（熔断仅一行 errors）、fix 归零无告警，是"1100 s 无人知晓"的组织性成因（t2 §1、§8.6）。
7. **方案不得引用 `memory.json` 的 `stuck_score` / `stuck_duration` / `reflex_active` 作为故障证据**；如需引用，必须同时标注"检测层伪影"与"版本边界 H1"。
